# 이벤트 분석 구현 현황

## 이상 징후 상관분석 — 우선 확인할 신호 (2026-11-02)

- 새 모듈 `core/triage_anomalies.py`가 파싱된 레코드를 **대상·출발지별 고정 15분 구간**으로 묶어 로컬 규칙으로만 상관 신호를 만든다. 대상 요청·AI 호출이 없고, 침해 성공이나 과거 대비 급증을 판정하지 않는다.
- 규칙: 경로 탐색 중 응답 차이(404 경로 3개 이상 + 200·206 혼재), 탐색 이후 공격 요청, 동일 경로의 차단·허용 혼재, 공격 탐지 요청의 5XX 반복(3건↑), 민감 파일·경로 탐색(3건↑), 여러 출발지의 경로 집중, 같은 출발지의 다중 대상 탐색.
- 각 신호는 근거 로그(`event_ids`)와 **확인 후보**(`candidate_ids`, 예: 404 사이의 200 응답만)를 구분한다. `IMPORTANT_ASSET` 자산이 포함되면 우선순위를 high로 올린다. 시각·대상이 없는 레코드는 상관에서 제외하고 `coverage`로 건수를 노출한다.
- `refresh_attack_summary`가 분석·수동 조사 반영 시마다 `result['anomaly_analysis']`를 재계산한다. 프론트는 "우선 확인할 이상 징후" 패널로 근거 로그 펼침과 **신호별 요청 일괄 테스트 전달**(`TriageWorkflow.findingQueue`, 화면 제외 필터 적용)을 제공한다.
- 검증: `backend/tests/test_triage_anomalies.py`가 후보 분리·시간순·구간 경계·대상 충돌 제외·빈 입력을 확인한다.

## 경로별 검증 후보 유지 (2026-11-02)

- 자산 기술 조사는 다수 URL의 재검증을 줄이고 영향을 판단하는 보조 근거다. 응답 헤더에 기술이 없다는 사실만으로 미사용이나 안전을 확정하지 않는다.
- 단순 경로 탐색도 파일이나 경로가 다르면 별개의 요청으로 유지한다. 서로 다른 경로를 반복 스캔이라는 이유만으로 대표 몇 건으로 압축하지 않는다.
- IPS 차단과 단순 경로 탐색 4xx는 각각 기본 검증 목록에서 제외하며, 화면에서 필터를 해제할 수 있다. 4xx는 경로의 실제 부재나 자산 안전의 확정 근거가 아니다.
- 필터 후 검증 URL 전달 시 완전히 동일한 URL만 중복 제거한다. 제외된 원본 이벤트도 통계·전체 목록·내보내기에 유지된다. 주소·요청 정보가 부족한 이벤트는 확인 필요로 표시한다.
- 검증: JS 흐름 테스트에서 서로 다른 23개 경로를 모두 전달하고 동일 URL만 하나로 합치는지 확인한다.

## CVE·제품군 인식 (2026-11-01)

- 기존 "요청/분석" 엔진의 **요청 전용 CVE 지문**(`analyzer._cve_identify_from_request`)을 새 모듈 `core/triage_cve.py`로 감싸 triage에 연결했다. 응답 본문이 필요 없어 로그 레코드에 맞는다. 로컬 규칙만 사용하며 대상 요청·AI 호출이 없다.
- 각 이벤트에 `cve`·`products`·`cve_source`를 부여한다. 우선순위: ① 장비 탐지명에 있는 CVE/제품명(신뢰 높음, `source=device`) → ② 요청 지문 추론(신뢰 중, `source=inferred`). 기존 `classify()` generic 분류(sqli/xss/cmdi 등, Log4Shell 등 헤더 공격 포함)는 그대로 유지한다.
- CVE ID → 제품군 매핑(log4j·struts·spring·weblogic·citrix·confluence·apache-httpd·laravel 등)으로 요청 지문에 서버 메타가 비는 OOB 계열(Log4Shell 등)도 제품군을 보완한다.
- 통계에 **CVE·제품군 카드**를 추가했다: CVE ID별 분포와 제품군별 레코드 수·차단/허용/불명·대상 수·연관 CVE. 분모는 CVE/제품을 식별한 레코드 수(`cve_records`)다.
- 이는 **공격 '시도' 식별일 뿐 성공·침해 판정이 아니다.** 장비 라벨과 EventProbe 추론을 출처로 구분하며, 제품명 단순 매칭의 저신뢰 가능성은 지문 기반과 분리한다.
- 한계: 응답 기반 제품 지문(Server 헤더·본문 마커·retire.js)은 로그에 응답이 없으면 적용하지 않는다. 요청 지문 카탈로그에 없는 CVE는 generic class로만 남는다.
- 검증: `test_triage_cve.py` 6개(탐지명/요청지문/Log4Shell 헤더/빈 입력/통계 집계/엔드투엔드) + 전체 트리아지 회귀 통과.

## 발생 이벤트 통계 (2026-11-01)

- `evtname` 우선 탐지명별 상위 10개와 기타를 원형 차트로 표시한다. 탐지명이 없으면 장비 탐지명을 사용한다.
- URL·본문의 공격 분류와 탐지명 패턴을 이용해 정보 수집성, 웹 공격, 애플리케이션 공격, 네트워크 공격, 기타/미분류로 분류한다. 이 분류는 휴리스틱이며 탐지의 진위나 공격 성공 판정이 아니다.
- 장비 종류가 명시된 경우에만 IPS·WAF·IDS로 집계한다. 장비별 차단·허용·불명 비율과 WAF·IDS의 HTTP 응답 코드(미기록 포함), 장비 응답 판정값을 별도로 표시한다. `result_status=Inconclusive`는 HTTP 상태 코드로 바꾸지 않는다.
- HTTP Host가 있으면 이를, 없으면 DST 주소를 대상으로 사용하여 상위 10개와 기타를 보여준다. HTTP 경로가 없는 IDS·IPS 로그도 대상과 탐지명이 있으면 집계하되 재요청 대상으로 사용하지 않는다.
- 같은 출발지의 여러 대상, 같은 대상의 여러 출발지, 한 출발지의 여러 공격 계열을 상관 후보로 보여준다. 임계값은 서로 다른 항목 3개이며, 입력 파일 밖의 관측은 알 수 없다.
- 모든 차트의 분모는 파싱된 레코드 수다. 장비의 `occurrences`/`cnt` 합계, 여러 장비의 중복 관측, 실제 공격 시도 횟수와 같다고 해석하지 않는다.
- AI 활용 확장 권장: 시간대별 급증과 평소 대비 편차, 출발지·대상·공격 계열의 연쇄, 차단 후 유사 허용 요청, 응답 코드 변화, 동일 탐지의 장비 간 불일치 설명. 외부 AI를 쓴다면 IP·호스트·URL·본문·헤더·원문을 제외한 집계 수치와 일반화된 범주만 전달하고, 소수 사례가 재식별되지 않도록 최소 집계 크기와 전송 전 미리보기를 적용한다. 현재 통계는 로컬 규칙 계산이며 AI 호출은 없다.
- 검증: 통계·분석·저장 관련 Python 회귀 테스트 43개와 JS 흐름·문법 검사.

## 공격 핵심 요약 보강 (2026-11-01)

- 분석 정책 `triage-3`: URL·쿼리 외에 명시적인 요청 헤더와 본문을 기존 공격 분류기로 검사한다. 요청 패턴이 없으면 알려진 탐지명으로 유형을 보완하고, 장비 탐지명이라는 출처를 표시한다.
- 상단에 공격 유형·대상별 중요도, 예상 영향, 대표 근거, 출발지·경로, 차단·허용 분포, 다음 확인 사항을 표시한다. 조사 순서 상위 5개 묶음을 먼저 보여주며 전체 이벤트는 분석표와 JSON에 남긴다.
- 공격 중요도와 재요청 우선순위를 별도로 유지한다. 차단된 고위험 공격도 높은 중요도로 표시하며 자동 재요청 대상으로 승격하지 않는다. 허용·불명 또는 혼재된 고위험 이벤트를 먼저 조사한다.
- 중요도 높음은 명령 실행·SQL 주입·파일 접근·인증 우회·SSRF·템플릿 주입 유형, 명시적인 높은 장비 심각도 또는 최신 중요 자산 정보에 근거한다. 수치형 벤더 심각도는 임의 환산하지 않는다. 이는 침해 확률이나 성공 판정이 아니다.
- 로그 레코드 수와 횟수 필드가 있는 레코드의 장비 보고 발생 횟수를 구분한다. 자산 대조 후 요약도 갱신하며, 예전 저장 기록은 원문 재분석 안내를 표시한다.
- 검증: 이벤트 분석·저장·캠페인·검증 준비 관련 Python 테스트 40개, JS 선택·그룹·중요도 정렬 회귀 테스트 및 문법 검사.

2026-11-01: 제안서 1~2단계의 읽기 전용 MVP 구현.

- 왼쪽 이벤트 분석 메뉴에서 로그 파일/붙여넣기 → 서버 분석 → 대상별 시간창 묶음 → 상세 필드/우선순위 필터 → JSON 내보내기.
- `/api/triage/analyze`는 최대 2MB/10,000건을 처리하며 서버에 배치를 저장하지 않는다. 대상 요청과 AI 호출은 없다.
- CEF, 인용 key/value WAF·IDS, JSON 배열/NDJSON 및 httpHost 또는 _raw로 시작하는 CSV를 지원한다. 다른 CSV 컬럼 순서/벤더 포맷은 추가 어댑터가 필요하다.
- 시간대를 포함한 ISO 시각은 15분 묶음으로 분류한다. 다른 시각 표기/시각 누락은 레코드별 보완 묶음이다.
- PCAP은 디코딩하지 않고 미분석 표시한다. 원문 필드와 탐지 문자열은 텍스트로 출력한다.
- 테스트: 벤더 동작/횟수, IDS 중첩 필드, 호스트 충돌, 오류 행, 혼재 증거, 4xx 예외, 용량/API 경계.

후속 범위: 벤더 시각/CEF severity 정규화, 광범위 CSV 어댑터, 중복 가져오기 이력, 자산 인벤토리 연결, 사용자별 저장/보존, 검증 계획과 실제 실행 연결, 수동 우선순위 변경 이력. 현재 화면은 이를 완료한 것으로 표시하지 않는다.

서버가 reload 없이 실행 중이면 백엔드 재시작 후 신규 API를 사용할 수 있다.


## 2차 구현: 자산 대조와 선택 검증

- 이벤트 상세에서 운영자가 확정한 URL을 입력하여 기존 관측 엔드포인트와 정확히 대조한다. 기존 작업공간 소유권 범위를 적용하며 미등록 자산을 저우선으로 강등하지 않는다.
- `/api/triage/prepare`는 GET 쿼리 요청에 대해 지원 유형·주입 키·URL을 검사하고 사건 계약과 최대 요청 수를 반환한다. 대상 요청/AI 호출/사건 저장은 없다.
- UI에서 계획과 요청 수를 확인하고 승인하면 기존 사건 생성 및 재검증 API를 호출한다. 이 시점에 사건과 실행 기록을 저장한다. 실행 링크로 기존 진행·중지·결과 화면에 연결한다.
- 인증 포함 URL, 중복 쿼리 키, fragment, 비 HTTP URL, 지원하지 않는 유형/파라미터는 준비 단계에서 거부한다. GET 외 메서드·본문 기반 요청은 수동 검토 안내를 표시한다.
- 로그 호스트에서 프로토콜을 임의 추정해 실행하지 않는다. 확정 URL은 사용자가 입력하며, 로그 자격정보는 재사용하지 않는다.
- 실행 실패 시 만들어진 사건을 유지해 같은 사건에서 재시도할 수 있다. 완료 이후 재검증 결과는 기존 사건 상태를 따른다.
- 입력을 수정하면 기존 계획 승인을 무효화하고 준비 응답 대기 중 수정된 입력에도 이전 계획을 적용하지 않는다.
- 검증: 분석·계획·자산·사건 회귀 테스트 총 58개 통과. JS 문법/Python 컴파일 검사 통과. 실제 대상 요청은 수행하지 않았다.

남은 범위는 운영 인벤토리의 중요도/스택/최신성 관리, 원문 보존/배치 저장, 벤더별 시각 및 포맷 확장, 중복 수집 관리, 우선순위 변경 이력이다. 새 화면은 현재 기존 엔드포인트 이력 대조를 제공하며 완전한 CMDB로 표시하지 않는다.


## 3차 구현: 운영 인벤토리와 선택 보관

- 운영 인벤토리 CSV 등록/갱신/조회/삭제: origin,service,contact,importance,stack,environment,verified_at. 500개까지 한 번에 검증하며 오류가 있으면 해당 가져오기를 전체 거부한다.
- origin 호스트가 하나의 자산에만 일치하고 호스트 충돌이 없을 때 연결한다. 30일 초과 확인 정보는 오래됨으로 표시한다. 신선한 high 자산은 정보 보완에서 검토 필요로 승격할 수 있지만, 미등록/오래된 자산은 감점하지 않는다.
- 분석 기록 저장은 선택 사항이다. 기본 7일, 1~30일 지정 가능하며 원문과 분석 결과를 함께 저장한다. 작업공간당 최대 100개 배치다.
- 동일 원문 SHA-256의 작업공간 내 중복 저장은 같은 기록을 반환하며 기한을 연장하지 않는다. 교차 파일은 파싱된 원본 필드의 fingerprint로 겹치는 이벤트 수를 표시하고 삭제하지 않는다. 장비 간 같은 통신 여부의 상관분석과는 다르다.
- 저장 기록 조회/불러오기/삭제를 제공한다. 불러온 결과는 저장 당시 정책/자산 정보 기준임을 화면에 표시한다.
- 만료 기록은 실행 중 60초 주기와 기록 접근 시 정리한다. 서버 중지 중에는 정리되지 않으며 다음 실행 때 정리한다. 삭제는 SQLite 논리 삭제이며 별도 백업/디스크 복구 방지까지 보증하지 않는다.
- DB 기본 경로는 기존 agent DB 옆 triage.sqlite3이며 TRIAGE_DB_PATH로 분리할 수 있다. 기존 agent DB 스키마는 변경하지 않는다.
- 작업공간 식별은 기존 ep_user / x-eventprobe-user 방식과 일치한다. 조회/삭제/중복은 해당 값으로 분리한다. 이 값은 자체 인증 수단이 아니며 공용 토큰 사용자 간 강한 격리를 의미하지 않는다.
- 로그 분석 자체는 여전히 대상 요청/AI 호출을 발생시키지 않는다. 일반 분석이 임시 입력을 자동 보존하지 않으며, 인벤토리 조회를 위해 빈 저장소 파일은 생성될 수 있다.

남은 확장: 벤더 시각/CEF 메타데이터 파싱 보강, 다양한 CSV 어댑터, 이벤트 우선순위 수동 변경 감사, 장비 간 요청 상관분석, 인증된 개인별 접근 체계.


## 대응 중심 UI 및 일괄 테스트 연결

- 로그 가져오기 → 종합 판단 → 대상별 접속 주소 확인/이벤트 선택 → 다중 대상 일괄 테스트로 연결한다. 분석 후 입력 영역은 접고 종합 판단을 앞에 표시한다.
- 종합 판단은 차단/허용/불명 분포, 검토 필요/정보 보완/재요청 저우선과 권장 대응을 규칙으로 요약한다. 침해 성공을 추정하지 않는다.
- 검토 필요 일괄 선택 또는 개별 선택을 지원한다. 저우선도 사용자가 직접 선택할 수 있다.
- 확정 origin을 입력해야 하며 GET 요청만 연결한다. 동일 URL은 1개로 합치되 원본 이벤트 연결은 모두 보존한다. 경로를 이용한 origin 이탈과 잘못된 URL은 전달 전에 거부한다.
- 기존 일괄 테스트의 다중 대상 화면에 URL을 채우고 GET/직접 입력 페이로드 없음/동시 1로 준비한다. 실제 전송은 사용자의 기존 테스트 시작 버튼으로 실행된다. 요청 헤더는 기존 설정을 사용하므로 화면에서 확인하도록 안내한다.
- 다중 테스트 완료 시 실제 실행 URL과 매칭한 원본 이벤트에 응답 코드/시각을 표시하고 bulkResults에 출처 연결을 남긴다. 연결은 현재 브라우저 세션 기준이며 저장된 분석 배치에 자동 소급 반영하지 않는다.
- 검증: 순수 UI 흐름 테스트(요약, 선택, 중복, 잘못된 origin/경로/메서드 거부) 및 JS 문법 검사 통과. 실제 대상 요청은 수행하지 않았다.


## 분석표와 검증 후보 중심으로 재구성

- 이벤트 카드를 대상/요청, 탐지 내용, 장비 처리/응답, 분석 판단, 레코드 수의 표로 교체했다.
- 동일 host/method/path/signature/action/status/priority의 로그를 묶고 검토 필요를 먼저 정렬한다. 다른 쿼리 값은 보존한다.
- 원문 전체 URL 또는 로그의 명시적인 scheme/80·443 포트로 접속 주소를 복원한다. 호스트 충돌/PCAP 미확인은 자동 복원에서 제외하고 보완 입력으로 남긴다.
- 접속 주소가 복원되는 검토 필요 GET 이벤트는 자동 선택한다. 저우선은 자동 선택하지 않는다. 사용자는 분석표에서 예외를 선택할 수 있다.
- 일괄 테스트는 선택된 요청을 전달하며 기존 실행 버튼에서 시작한다. 검증 결과 응답 코드를 원래 분석표에 표시한다.
- 행별 별도 파라미터 검증 폼은 주 화면에서 제거했다. 기본 흐름은 분석표 확인과 일괄 테스트 연결이다.


## 대량 스캔 대응: 행위 묶음

- 대상/출발지 × 고정 15분 시간창으로 관측 이벤트를 묶는다. 10레코드·5경로 이상을 넓은 경로 탐색으로, 같은 대상 3출발지·5경로 이상을 여러 출발지 탐색 후보로 표시한다. 출발지 한 곳의 3자산 이상 탐색과 10레코드·3유형 이상 탐색도 표시한다.
- 숫자는 초기 휴리스틱이며 입력 파일 내 관측치다. 중복 레코드, NAT/프록시, 시간창 경계와 수집 누락의 영향을 받는다. 실제 캠페인/동일 공격자 확정 기능은 아니다.
- 차단·허용·불명 분포 및 운영 대응 안내를 제공한다. 전부 차단된 묶음은 대표 재요청을 추천하지 않는다. 그 외에는 허용 또는 검토 필요 GET 요청에서 최대 3개를 선정하고 선택 버튼으로 기존 일괄 테스트에 연결한다.
- AI 사용 여부는 로그만으로 판별 불가로 표시한다. 빠른 적응형 요청 생성, 장기 저속 탐색, 교차 파일/장비 상관분석은 아직 구현하지 않았다.
- 근거: MITRE Active Scanning https://attack.mitre.org/techniques/T1595/ 및 Wordlist Scanning https://attack.mitre.org/techniques/T1595/003/ . AI 공격 도구 활용 동향 참고: Microsoft https://www.microsoft.com/en-us/security/blog/2026/03/06/ai-as-tradecraft-how-threat-actors-operationalize-ai/ . 이 동향을 AI 사용 판별 규칙으로 전용하지 않는다.


## 웹 기술 조사 결과 통계 연결

- 이벤트 분석 통계에 호스트/DST 사용 기술 카드를 추가했다. 대상 수, 조사 완료/실패/미조사 수와 식별 대상 수를 구분한다.
- 대상별 Host/DST, 연결된 이벤트 수, 인벤토리 등록 기술/오래됨 여부, 실제 조사 기술/HTTP 상태, 조사 시각을 표시한다.
- 실제 관측 기술 분포는 레코드 수가 아닌 고유 대상 수로 집계하며 동일 대상의 동일 기술은 중복 집계하지 않는다. 등록 기술을 실제 조사 결과로 합산하지 않는다.
- 기술 확인 성공/실패 후 통계가 즉시 갱신된다. 미식별과 요청 실패를 구분하며 추가 대상 요청은 기존 웹 기술 확인 버튼에서만 발생한다.
- 조사 결과는 현재 분석 화면 세션에 유지되며 기존 JSON 내보내기에 이벤트별 기술 정보가 포함되더라도 조사 시각/상태 통계는 저장된 배치로 자동 영속화하지 않는다.


## 로그 분석 직후 웹 기술 자동 조사

- 로그 분석 버튼이 분석 후 현재 이벤트와 연결된 등록 인벤토리 origin의 웹 기술 조사를 자동 실행한다. 대상별 중복 제거, 동시 2개, 최대 20개이며 초과 대상은 개별 확인으로 남긴다.
- 기존 등록 자산 검사 API를 그대로 사용한다. 미등록 호스트/DST로 자동 요청을 확장하지 않으며, 등록 연결이 없으면 이유를 화면에 표시한다.
- 진행률/실패 건수/중지 버튼을 제공한다. 한 대상 실패는 다른 대상의 조사를 중단하지 않으며 중지 시 브라우저 요청을 취소하고 새 대상을 시작하지 않는다. 이미 서버에 전달된 요청은 최대 기존 5초 timeout까지 진행될 수 있다.
- 결과마다 기술 통계와 기술 일치 선별을 즉시 갱신한다. 성공적인 기술 관측 자체가 취약 성공 증거는 아니다. 실패 시 분석 결과는 그대로 이용 가능하다.
- 테스트는 가상 조사 함수로 중복 제거·동시성·대상 한도·실패 격리·중지·미등록 제외를 확인했다. 실제 대상 기술 조사는 실행하지 않았다.


## 미등록 대상 수동 웹 기술 확인 허용

- 안전성 재검토 결과, 웹 기술 조사는 리다이렉트·본문·쿠키·인증정보를 보내지 않는 헤더 전용 GET 1회이며, 도구의 기존 일괄/다중 테스트(실제 공격 페이로드 전송)보다 덜 침습적이라 "등록 자산만" 제약은 과도했다. 조사 대상은 공격 출발지가 아니라 로그의 대상 호스트(자사 자산)다.
- `/technology-probe`에서 "등록 origin만(403)" 제약을 제거하고 URL 형식 검증(scheme·host만, 경로/쿼리/인증정보 금지)은 유지한다. 분석가가 명시적으로 요청한 단일 헤더 전용 GET은 미등록 대상이어도 허용한다.
- 자동 일괄 조사는 여전히 등록 자산으로만 제한한다(임의 로그 호스트 무차별 자동 요청 방지). 미등록 대상은 기술 카드의 수동 "웹 기술 확인" 버튼으로만 조사하며, 전송 전 확인 팝업을 띄우고 내부망 주소로 보이면 경고한다. 동시 2개·최대 20개·5초 timeout 상한은 유지한다.
- 검증: `/technology-probe`가 미등록 origin도 헤더 전용 GET으로 조사하고 잘못된 접속 주소는 422로 거부하는 단위 테스트, 미등록 호스트에 수동 버튼이 노출되는 프런트 확인.


## 미사용 웹 기술 자동 노이즈 제외

- 요청 경로가 특정 제품(wordpress·phpmyadmin·next.js·spring·exchange)을 겨냥하는데 관측된 웹 기술에 그 제품이 없으면 `TECH_MISMATCH`로 기본 검증 대상에서 제외한다. 노이즈 제외 필터에 "미사용 웹 기술" 토글(기본 on)을 추가했다.
- 관측 기술을 아는 경우에만 '미사용'으로 판단한다. 기술 미관측(빈 목록)은 부재의 증거가 아니므로 제외하지 않으며, 중요 자산·혼재 기록은 제외하지 않는다. 헤더 지문은 불완전하므로 설명에 '부재로 단정하지 않음'을 명시하고, 제외 이벤트는 토글로 되돌릴 수 있으며 전체 목록·통계·원본에 남는다('안전' 판정 아님).
- 수동 웹 기술 확인 결과가 즉시 반영되도록 `applyTechnology`를 수정했다. 이전에는 `inventory.origin`이 일치하는 이벤트만 갱신해 미등록 호스트의 수동 조사 결과가 반영되지 않았는데, 이제 (추론/입력)origin이 일치하는 모든 이벤트에 관측 기술을 반영하고 TECH_MATCH/TECH_MISMATCH를 재계산한 뒤 다시 렌더링한다. 자동 일괄 조사도 동일 경로를 쓴다.
- 검증: TECH_MISMATCH 스크리닝(일치 유지·미관측 보류·중요자산 보존) 단위 테스트, 트리아지 백엔드 92개·프런트 173개·워크플로 cjs 통과. 등록 자산(stack=nginx)에 /wp-login.php 로그가 자동으로 "미사용 웹 기술"로 제외되는 것을 실제 화면에서 확인.


## 통계·스캔 요약 의미 전달 개선 (실데이터 기반)

- 유형 분류(`event_family`) 보강: SSRF·버퍼 오버플로·OGNL/JNDI/log4j·deserialize·exploit·code execution 등 IDS/IPS 시그니처 키워드를 인식하고, 이름으로 못 가린 CVE/제품 익스플로잇은 애플리케이션 공격으로 분류한다. 실제 로그에서 "기타/미분류"가 크게 줄었다(샘플 133→40).
- 탐지명 정규화(`display_name`): 장비가 집계한 비식별 라벨(예: Imperva "Multiple signatures from <IP>")을 "다수 시그니처(장비 집계) · 출발지 <IP>"로 읽기 쉽게 표기한다.
- 스캔 시도 요약 시간창: 15분 버킷 인덱스(예: 1992779) 대신 사람이 읽는 KST 시간 범위로 표기한다. 같은 출발지/대상의 활동을 버킷별로 쪼개지 않고 하나의 캠페인으로 병합하고 구간 수를 함께 보여준다(인접/산발 버킷 분할 완화).
- 모두 로컬 규칙 계산이며 대상 요청·AI 호출이 없다. 검증: 트리아지 백엔드 92개·프런트 173개·워크플로 cjs 통과, 실제 4.csv 분석과 라이브 화면 확인.


## CVE·제품군을 빈도 → 결과(미차단) 중심으로 재구성

- CVE·제품군 "공격 시도" 통계가 단순 빈도(어떤 CVE가 몇 번 스캔됐나)라 트리아지 가치가 낮았다. 차단된 시도는 대개 인터넷 배경 스캔이고, 봐야 할 것은 차단되지 않은(허용·불명) 시도이기 때문.
- CVE별·제품군별을 **미차단(허용+불명) 우선**으로 정렬하고, 각 항목에 차단/미차단 수와 대상 수를 표기한다. 헤드라인에 `CVE/제품 식별 N건 · 미차단(허용·불명) M건`을 보여준다. "차단은 배경 스캔, 미차단·실제 운영 자산을 먼저 확인"하도록 안내한다.
- 이는 성공/침해 판정이 아니다. 미차단은 '차단 기록이 없음'(IDS 탐지전용 포함)일 뿐이며, 실제 도달·취약은 자산 확인/재검증으로 가린다.
- 실데이터(4.csv): CVE 식별 194건 중 미차단 129건, CVE-2022-26134·2021-44228 등 전부 미차단 항목이 상위로, ProxyLogon(대부분 차단)은 하위로 재배치. 검증: 트리아지 백엔드 92·프런트 173·cjs 통과 + 라이브 화면.


## 자산 기술 조사: 기존 분석기 재사용

- 분석 직후 등록 여부와 관계없이 대상 origin별 GET / 1회, 동시 2개로 조사한다. 별도 경로 탐색·재시도·리다이렉트 추적은 하지 않는다.
- 요청/분석의 기술 스택·WAF·SPA 식별 함수를 로컬에서 재사용한다. 공격 판정 전체 엔진은 실행하지 않는다. 텍스트 응답만 최대 128KiB 읽고 전체 요청 수명은 10초로 제한한다.
- 기술 헤더 및 SPA 본문 패턴을 통합한다. 본문 패턴은 잠정 근거로 표시하며 버전이나 CVE 취약 여부를 확정하지 않는다.
- 응답 본문·쿠키·헤더 원문은 API 결과로 반환하거나 저장하지 않는다. 외부 AI/평판/지문 서비스 호출은 없다. 대상 서버에는 일반 GET / 요청과 조사 서버의 네트워크 주소가 보인다.
- 외부 실행 도구는 이번 변경에 추가하지 않았다. 기존 엔진 재사용 이후 식별 범위가 부족한 경우 별도 기술 지문 도구의 로컬 실행을 검토한다.
- 테스트는 모의 HTTP 응답으로 요청 수, 리다이렉트 비활성, 환경 프록시 미사용, 본문 상한, 원문 미반환을 확인한다.
