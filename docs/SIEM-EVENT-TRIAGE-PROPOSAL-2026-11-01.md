# SIEM 보안 이벤트 분석 및 선별 검증 기능 제안서

작성일: 2026-11-01 · 대상: ARTEX / EventProbe · 상태: 구현 착수용 제안서

## 1. 제안 요약

SIEM에서 조회한 IPS·WAF·IDS 로그를 가져와 **무엇이 발생했고, 어떤 이벤트를 먼저 검토하며, 무엇을 실제로 검증할지** 정리하는 기능을 제안한다. 기존 일괄 테스트 앞에 별도 **「이벤트 분석」 탭**을 두고, 로그 분석 → 대상별 묶음 → 우선순위 검토 → 선택한 요청의 검증으로 연결한다.

현재 일괄 테스트는 로그에서 URL을 추출해 테스트 대상으로 전달하는 데 초점이 있다. 차단 여부, 탐지명, 발생 횟수, 응답 코드, 자산의 중요도를 함께 판단하는 흐름이 부족하다. 이를 보완하되 기존 요청 분석·사건·검증 엔진은 가능한 범위에서 재사용한다.

기대 효과는 반복 스캔을 읽고 재검증하는 시간을 줄이고, 검증이 필요한 이벤트의 근거를 분명하게 만드는 것이다. 절감률은 실측 전 확정하지 않는다. **저우선순위는 안전 판정이 아니며, 로그 분석만으로 침해 성공을 확정하지 않는다.**

본 문서는 Claude 작업계획과 초안, 제공된 세 로그, 현재 작업 트리의 코드를 대조해 완성했다. 아래 신규 화면·규칙·API는 제안 사항이며 구현 완료 기능을 뜻하지 않는다.

## 2. 요구사항과 대응

| 요구 | 제안 기능 | 사용자에게 보이는 결과 |
|---|---|---|
| IPS 차단 이벤트의 불필요한 검증 축소 | 장비별 차단 필드 정규화, 차단 신뢰도 및 반대 증거 확인 | `장비 차단 기록 · 재요청 저우선` |
| 단순 스캔과 4xx 선별 | 단순 GET·404 등을 조건부 저우선 처리; 다른 4xx는 구분 | 제외 이유와 예외를 확인할 수 있는 접힌 목록 |
| 다수 스캔 분류 | 목적지 서비스 중심으로 출발지·시간·공격 유형별 묶음 | 호스트별 요약과 대표 이벤트 |
| 전체 정리와 불필요 이벤트 필터 | 검토 필요·정보 보완·저우선 분리, 중복은 묶음 처리 | 전체 수량과 처리 근거를 함께 표시 |
| 기존 Request/Analysis 분류 재사용 | 요청 유형 분류와 민감파일 탐지 재사용 | 유형과 일치한 근거 표시 |
| 자산 정보 활용 | 기존 관측 자산과 운영 인벤토리를 구분해 대조 | 중요도·소유자·스택·정보 최신성 표시 |
| 추가 고려사항 | 원문 추적, 파서 오류, 프록시, 중복, 권한, 요청 예산, 결과 감사 | 누락과 잘못된 자동 실행을 줄이는 운영 흐름 |

## 3. 현재 기능과 재사용 범위

아래 위치는 작성 시점의 작업 트리를 기준으로 확인했다. 코드 변경에 대비해 줄 번호보다 함수명을 우선한다.

| 코드 | 확인 내용 | 제안에서의 사용 |
|---|---|---|
| [app.js](../frontend/static/js/app.js), `readSplunkFile`, `extractUrlFromLogLine`, `fillMultiFromLog` | 브라우저에서 파일을 읽고 host/path/query/port로 URL을 만든다. 구조화된 이벤트 전체를 유지하는 반환값은 아니다. | 기존 가져오기 진입점 공유, 새 분석 흐름으로 분기 |
| [api.py](../backend/routers/api.py), `BulkRequest`, `MultiTargetRequest` | 일괄·다중 대상 실행 모델 | 검증 실행 연결에 사용; 로그 이벤트 저장 모델과 구분 |
| [classify.py](../backend/core/classify.py), `classify` | 요청의 공격 유형을 분류한다. 취약 여부를 판정하지 않는다. | 경로·쿼리·확보된 본문/헤더의 유형 힌트 |
| 같은 파일, `is_direct_file_probe` | `.env`, `.git/config` 등 제한된 민감파일 경로를 인식한다. 범용 스캐너 탐지기가 아니다. | 민감파일 탐색 보조 규칙 |
| [agent_assets.py](../backend/core/agent_assets.py), `asset_shape` | origin·method·path·query key로 자산 식별자를 만든다. query 값은 식별에 넣지 않는다. | 기존 엔드포인트와의 연결; 이벤트 중복 제거에는 별도 키 필요 |
| [analyzer.py](../backend/core/analyzer.py), `detect_stack` | 응답 헤더 기반 기술 정보 추론 | 응답 없는 SIEM 로그의 스택을 이 함수로 추정하지 않음 |
| [agent.py](../backend/core/agent.py), `verify_incident` | 지원 유형·요청·주입 위치가 있어야 재검증 실행을 만들 수 있다. AI 호출 예산은 0이다. | 재구성 가능한 요청의 선택 검증 |
| [agent_incidents.py](../backend/core/agent_incidents.py), `build_incident_trace` | 미검증·검증 중·판정불가·재현·의심·이번 실행에서 미재현을 구분한다. | 검증 결과 상태 재사용 |
| [agent_store.py](../backend/core/agent_store.py), `record_manual_traffic_batch` | 수동 트래픽 source 허용 목록에는 현재 `siem`이 없다. | 관측 로그는 신규 이벤트 저장소로 분리; 실행 이력 연결 시 source 확장 검토 |

`classify`가 현재 규칙으로 직접 산출하는 주요 유형은 authbypass/cmdi/lfi/xss/ssti/ssrf/sqli/nosql/xmlrpc이다. redirect 힌트의 정의만으로 해당 유형이 출력된다고 가정하면 안 된다. IDOR·JWT·XXE 등은 별도 근거와 어댑터가 필요하다. 미분류·복수 유형은 노이즈 근거가 아니라 검토할 불확실성이다.

현재 IDS 내부 파서는 첫 `==`를 기준으로 나누므로 **뒤의 base64 `==` 자체가 반드시 깨진다는 초안의 지적은 적용하지 않는다.** 다만 인용부호·이스케이프·필드 경계·불완전 입력을 포함한 파서 검증은 필요하다.

## 4. 제공 로그 세 건에 대한 적용 결과

민감한 IP·실제 호스트·요청 식별값·원문 PCAP은 제안서에 복제하지 않는다. 아래 값은 판단에 필요한 필드만 발췌한 것이다. 세 건은 서로 다른 시각에 발생했으며, 예시의 공통 호스트 문자열만으로 동일 캠페인이라 판단하지 않는다.

### 4.1 IPS: TippingPoint / curl 페이지 조회 탐지

| 항목 | 확인한 내용 |
|---|---|
| 명시적 동작 | `act=Permit` → 허용 기록. 차단으로 분류하면 안 됨 |
| 탐지·요청 | `HTTP: Curl Web Page Retrieval Attempt`, `GET`, 다운로드 형태 경로 |
| 심각도·횟수 | CEF severity `1`, `cnt=1`; 벤더 원값 유지 |
| 응답 정보 | HTTP 응답 코드 없음 |
| 부가 근거 | PCAP을 로컬에서 디코딩하면 HTTP 요청 및 `curl/8.22.0` 확인 가능 |
| 불확실성 | 정규화 dhost와 PCAP Host가 다름. 관측 src·변환 주소·XFF의 의미도 분리 필요 |

**초기 처리: 정보 보완.** curl 사용과 Permit만으로 공격 성공이나 정상 통신을 확정할 수 없다. 자산 소유자, 다운로드 서비스의 정상 용도, 해당 시간의 응답/접근 기록을 먼저 대조한다. 정상 작업으로 확인되면 저우선으로 전환하고 확인 근거를 남긴다. 호스트 충돌 해소 전 자동 재전송은 금지한다.

시간은 수집 외피의 `04:06:54+09:00`와 CEF `rt`의 `04:06:33.804+09:00`를 별도 보관한다. 약 20.2초 차이를 공격 지연이나 장비 오류로 단정하지 않는다.

### 4.2 WAF: Imperva / .env 파일 접근

| 항목 | 확인한 내용 |
|---|---|
| 명시적 동작 | `disposition=Block`; `action=N/A`가 이를 덮어쓰면 안 됨 |
| 탐지·요청 | `Distributed .env file access(+)`, `GET /sites/all/libraries/mailchimp/.env` |
| 응답·횟수 | `resultCode=404`, `occurrences=13` |
| 심각도 | `alertSev=High`; 검토 우선순위와 별도로 유지 |
| 불확실성 | 404의 생성 주체 불명. `httpHost`와 헤더 Host 불일치, XFF 중복 존재 |

**초기 처리: 재요청 저우선 + 식별정보 보완 표시.** 이 로그는 장비의 차단 기록이 명확하므로 같은 요청을 즉시 재전송할 가치는 낮다. 단, 404를 오리진의 파일 부재 증거로 바꾸지 않는다. 동일 대상에서 허용된 유사 요청, 다른 경로의 성공 정황, 중요한 자산의 이상 징후가 발견되면 그룹을 검토 대상으로 올린다.

`occurrences=13`은 장비가 보고한 발생 횟수다. 입력 레코드는 1건이며 13개의 독립 로그가 확보된 것은 아니다. 원문 `Header-Value`에는 쉼표와 중복 헤더가 들어 있으므로 단순 쉼표 분리로 파싱하지 않는다. UA의 봇 이름도 발신자 신원 보증이 아니다.

### 4.3 IDS: ZGrab 스캐너 탐지

| 항목 | 확인한 내용 |
|---|---|
| 탐지·요청 | `HTTP: ZGrab Application Layer Scanner Traffic Detected`, `GET /owa/auth/x.js` |
| UA | `Mozilla/5.0 zgrab/0.x` |
| 동작·응답 | 차단/허용 필드 없음, HTTP 상태 코드 없음 |
| 장비 판정 | `result_status=Inconclusive`, severity `Low`, confidence `6` |
| 대상 | `destination_ip=TEST.IP`는 유효 IP가 아닌 예시 치환값; HTTP Host는 별도 존재 |

**초기 처리: 정보 보완.** OWA/Exchange 관련 탐색 후보로 묶되 실제 Exchange 운영 여부와 응답 기록을 확인한다. Low·zgrab만으로 제외하지 않는다. confidence 6은 척도 정의가 없으므로 60% 또는 높은 신뢰도로 변환하지 않는다. `Inconclusive`도 이 도구가 실행한 검증 결과와 구분한다.

출발지 IP와 `source_proxy_ip`는 각각 유지한다. 제공 출발지의 `172.180.*` 대역을 `172.*`라는 이유만으로 사설 IP로 처리해서는 안 된다. 대상 주소가 확정되기 전에는 재검증 후보를 실행 가능한 URL로 변환하지 않는다.

### 4.4 세 샘플의 화면 요약 예시

`입력 레코드 3 · 파싱 성공 3 · 재요청 저우선 1 · 정보 보완 2 · 즉시 실행 가능 0`

이는 제안 규칙을 샘플에 수동 적용한 예상 결과다. 구현된 분석기의 측정 결과가 아니다. 장비별 발생 횟수는 IPS 1 / WAF 13 / IDS 1로 별도 표시하며, 장비 간 중복 가능성이 있어 이를 독립 공격 15건으로 표기하지 않는다.

## 5. 선별 규칙과 우선순위

### 5.1 세 가지 판단을 분리한다

1. **분석 우선순위:** 검토 필요 / 정보 보완 / 재요청 저우선.
2. **실행 준비 상태:** 대상 미확정 / 요청 정보 부족 / 범위 밖 / 실행 준비 가능.
3. **검증 결과:** 기존 사건 상태를 사용. 로그 관측만으로 `reproduced`를 부여하지 않음.

따라서 차단된 WAF 이벤트는 재요청 저우선이면서 대상 미확정일 수 있다. 중요한데 실행 정보가 없는 이벤트도 검토 목록 상단에 남을 수 있다.

### 5.2 규칙 적용 순서

| 순서 | 조건 | 처리 |
|---|---|---|
| 1 | 파싱 실패·필드 충돌·주소/시각 불명 | 실패 또는 보완 목록 유지; 추정으로 실행 정보를 채우지 않음 |
| 2 | 동일 대상의 반대 증거: 허용 요청, 기존 확정 발견, 응답 내용의 이상 등 | 관련 그룹 검토 승격. 단일 차단 로그가 전체 그룹을 숨기지 않음 |
| 3 | 신뢰 가능한 장비별 필드가 명시적 차단이며 반대 증거 없음 | 재요청 저우선. 장비 기록이라는 근거를 표시 |
| 4 | 단순 조회 스캔 + 404/410 + 주입 흔적 없음 + 상태 출처 신뢰 가능 | 조건부 저우선. 낮춘 이유와 예외를 기록 |
| 5 | 401/403/429/기타 4xx, 5xx, 상태 없음 | 일괄 제외하지 않음. 인증·속도제한·오류 등 맥락 검토 |
| 6 | 민감파일 경로 + 2xx, 주입 공격 흔적, 중요 자산 관련 | 검토 필요. 성공 판정은 응답 증거/검증 이후 |
| 7 | 미분류, 유형 충돌, 자산 정보 없음/오래됨 | 정보 보완. 미등록이라는 이유만으로 감점하지 않음 |

404는 존재를 숨기기 위해 반환될 수도 있고, 403은 그 자체로 취약 또는 차단 장비 개입을 입증하지 않는다. 따라서 모든 4xx를 동일하게 제외하지 않는다. [HTTP 의미 규격 RFC 9110 §15.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5)

`blocked`/`allowed` 정규화는 장비별 필드 매핑을 거친다. 필드 부재·알 수 없는 어휘는 `unknown`으로 남긴다. Splunk CIM의 Intrusion Detection도 장비 동작을 별도 action 필드로 다룬다. [Splunk CIM Intrusion Detection](https://help.splunk.com/en/splunk-enterprise/common-information-model/6.1/data-models/intrusion-detection)

### 5.3 점수 도입 범위

MVP에서는 설명 가능한 규칙과 버킷을 먼저 구현한다. 검증되지 않은 가중합으로 이벤트를 자동 제외하지 않는다. 같은 버킷 안에서는 중요 자산, 반대 증거, 신뢰 가능한 최신 시각, 발생 집중도를 순서대로 사용한다. 불확실성은 검토 근거이며 감점 사유가 아니다.

운영자가 판정한 표본이 쌓인 뒤 점수제를 추가한다. 각 요소·가중치·정책 버전·기여도를 표시하고, 기존 규칙 대비 누락률을 평가한다. 2xx, 스캐너 UA, CDN 여부, 검증 엔진 지원 여부를 단독 성공/무해 판단이나 강제 제외 조건으로 사용하지 않는다.

## 6. 정규화와 묶음 설계

### 6.1 정규화 이벤트

| 필드군 | 저장할 정보 |
|---|---|
| 추적 | event_id, batch_id, 파일 해시, 행/레코드 위치, 원본 이벤트 ID, 파서 버전 |
| 시간 | 원본 시각·시간대·정규화 시각, 수집 시각, 채택 근거와 차이 |
| 장비 | 벤더·제품·장비 식별자, 원본 탐지명/ID, 원본 severity/confidence와 매핑 버전 |
| 동작 | 원본 필드명/값, normalized action, 신뢰도, 충돌 목록 |
| 출발지 | 관측 IP, 변환 IP, 프록시 IP, XFF 원본 순서, 신뢰된 클라이언트 IP(확정 시만) |
| 목적지 | dst_ip/port, host 후보와 출처, 확정 서비스 식별자, asset_id(선택) |
| 요청 | method, path, query, 확보한 헤더/본문의 존재 여부, 프로토콜 근거 |
| 응답 | http_status, 상태를 기록한 장비, edge/origin/unknown, 응답 증거 유무 |
| 집계 | 입력 레코드 수와 vendor occurrence count를 분리 |
| 판단 | 유형 후보, 우선순위, reason_codes, 실행 준비 상태, 수동 변경 이력 |

모든 정규화 값은 원본 필드와 연결한다. `N/A`와 누락은 0·허용·정상으로 바꾸지 않는다. 장비별 severity 척도는 운영 매핑을 확인하기 전 원값만 표시한다.

**샘플로 확인한 매핑:**

| 의미 | IPS CEF | Imperva WAF | IDS 예시 |
|---|---|---|---|
| 동작 | `act=Permit` → allowed | `disposition=Block` → blocked | 없음 → unknown |
| 응답 코드 | 없음 | `resultCode=404` | 없음 (`result_status`는 상태 코드가 아님) |
| 대상 호스트 | `dhost` + PCAP Host 후보 | `httpHost` + Header-Value의 Host 후보 | layer_7_data의 `HTTP Host` |
| 경로·메서드 | `request`, `requestMethod` | `url`, `webMethod`, `webQuery` | `HTTP URI`, `HTTP Request Method` |
| 발생 횟수 | `cnt` | `occurrences` | `attack_count` |
| 심각도 | CEF header severity | `alertSev` | `attack_severity` |

CEF는 이스케이프된 구분자와 값 내부 `=`를 처리한다. WAF는 필드별 경계와 인용 여부를 처리하고 Header-Value 원문을 별도로 보존한다. IDS의 중첩 문자열은 첫 구분자 이후 값을 보존한다. CSV·JSON·NDJSON도 입력 어댑터로 지원한다. 파싱 실패는 누락시키지 않고 위치·이유·건수를 표시한다.

PCAP은 선택적 로컬 분석 기능으로 분리한다. MVP는 존재 여부만 보존할 수 있으며, 파싱을 제공할 때는 크기 제한과 격리된 디코딩을 적용한다. **패킷을 재전송하지 않는다.**

### 6.2 호스트·프록시·자산 연결

서로 다른 Host를 덮어쓰지 않는다. NAT/CDN/리버스 프록시 관계는 운영자가 등록한 매핑이 있을 때만 연결한다. 포트만으로 외부 접속 프로토콜이 확정됐다고 보지 않는다. 로그에 있는 URL·Host·리다이렉트 주소는 실행 권한의 근거가 아니다.

XFF는 신뢰된 프록시 체인 설정이 있을 때만 클라이언트 식별에 사용한다. 설정이 없으면 관측 IP와 전달된 헤더를 병렬로 표시한다. IPv4/IPv6 파싱은 표준 주소 라이브러리를 사용한다.

### 6.3 묶음과 중복은 구분한다

- 기본 묶음: 확정된 목적지 서비스 + 조정 가능한 시간창(초기 제안 15분). 출발지·공격 유형·장비별 하위 보기 제공.
- 시간 불명·host 충돌 이벤트는 보완 묶음에 둔다. 단순 문자열 일치만으로 서비스/캠페인을 합치지 않는다.
- 같은 파일 재가져오기: 파일 해시와 레코드 위치로 멱등 처리. 교차 파일은 장비 ID·원본 이벤트 ID·시각 등을 함께 사용한다.
- 서로 다른 장비가 본 동일 요청은 연관 후보로 연결하되 독립 증거를 삭제하지 않는다.
- `asset_shape`는 같은 엔드포인트 연결에 사용한다. `id=1`과 공격 페이로드의 이벤트 원문을 같은 것으로 삭제하지 않는다.
- 대표 요청은 실행 가능한 것 중 유형·경로·결과가 다른 1~3건을 우선 제안한다. 숨겨진 나머지 건수와 선정 이유를 펼쳐 볼 수 있게 한다.

## 7. 자산 정보 활용

기존 Assets는 관측된 요청에서 만들어진 엔드포인트 목록이다. 회사 전체 자산을 보증하는 CMDB로 취급하지 않는다. 따라서 미등록 대상은 정보 부족이며, 불필요 검증 대상으로 자동 분류하지 않는다.

초기 운영 인벤토리는 소량 CSV 가져오기로 시작한다. 서비스명, host/IP 별칭, 담당자, 중요도, 기술 스택, 운영/시험 환경, 허용 검증 범위, 출처, 확인 시각을 포함한다. 정보가 오래되거나 충돌하면 스택 불일치 감점을 적용하지 않는다. 예를 들어 OWA 경로를 스캔했어도 Exchange가 없다는 최신 운영 근거가 있어야 관련성이 낮다는 보조 판단이 가능하다.

CDN은 요청 전달 계층이지 무해함의 증거가 아니다. 현재 웹서버 헤더도 과거 이벤트 시점의 스택을 보증하지 않으므로 시점을 함께 표시한다.

## 8. 화면 제안과 기존 탭 연결

**별도 「이벤트 분석」 탭을 권고한다.** 기존 일괄 테스트는 실행이 목적이고, 새 기능은 로그를 읽고 실행 대상을 줄이는 것이 목적이다. 가져오기 직후 요청이 나가는 혼동을 줄이기 위해 화면을 분리한다.

화면 설명: **“보안 로그를 묶어 확인하고, 필요한 요청만 골라 검증합니다.”**

1. **로그 가져오기:** 파일/붙여넣기, 형식 자동 감지, 분석 범위·파싱 결과 미리보기. 분석 중 대상 요청 0건 표시.
2. **전체 요약:** 입력 레코드·오류·그룹·검토 필요·정보 보완·저우선 건수. 장비 발생 횟수는 별도 표시.
3. **대상별 목록:** 서비스, 탐지 유형, 차단/허용/불명 비율, 응답 분포, 자산 중요도, 우선순위 이유.
4. **상세 패널:** 원본 필드 ↔ 정규화 값, 시간 흐름, 충돌·누락, 대표 요청, 동일 그룹의 나머지 이벤트.
5. **검증 준비:** 선택 요청과 목적지·검증 방식·예상 최대 요청 수·자격정보 필요 여부 확인 후 실행.
6. **결과:** 기존 사건/발견 화면에 연결. 실행하지 않은 이벤트와 재현되지 않은 이벤트를 구분.

저우선 목록은 기본 접되 언제든 펼쳐 보고 제외를 해제할 수 있게 한다. 사용자가 우선순위를 바꾸면 원래 판단과 변경 이유를 유지한다. 버튼은 `로그 분석`, `보완 정보 확인`, `선택 항목 검증 준비`, `검증 실행`처럼 동작을 명확히 쓴다.

기존 일괄 테스트에는 `로그 분석 후 선택하기` 진입점을 추가한다. `readSplunkFile`이 기존 URL 변환과 새 이벤트 분석을 선택하도록 변경한다. 기존 실행 흐름을 조용히 새 규칙으로 대체하지 않는다.

## 9. 구현 구조와 검증 연결

### 9.1 신규 구성 제안

`파일 → 형식별 파서 → 정규화/품질 검사 → 자산 대조 → 그룹/규칙 → 화면 검토 → 검증 계획 → 기존 실행 엔진 → 사건 결과`

신규 모듈은 `backend/core/triage/` 아래 parsers, models, rules, grouping, planning으로 나누고, 라우터와 화면 모듈을 분리한다. 이름은 구현 시 저장소 관례에 맞춘다.

API 초안:

| API | 역할 |
|---|---|
| `POST /api/triage/import` | 제한 크기의 입력 분석, batch_id와 파싱 요약 반환 |
| `GET /api/triage/batches/{id}/groups` | 소유자 범위 안에서 요약/필터/페이지 조회 |
| `GET /api/triage/events/{id}` | 필드 출처·판단 근거·허용된 원문 조회 |
| `POST /api/triage/validation-plans` | 선택 이벤트로 실행 가능한 계획 작성. 요청 전송 없음 |
| `POST /api/triage/validation-plans/{id}/execute` | 승인된 계획·범위·예산 재확인 후 기존 엔진 호출 |

계획에는 원본 이벤트 ID, 확정 목적지, 메서드, 검증 유형, 주입 위치, 최대 요청 수, 정책 버전, 만료 시각을 묶는다. 내용이 변경되면 실행 전 다시 확인한다. 기존 `verify_incident`의 고정 계획 생성이 이 전체 승인 절차를 대신한다고 가정하지 않는다.

### 9.2 자동으로 연결할 수 있는 범위

MVP는 요청 URL·메서드·주입 위치가 복원되고 기존 엔진이 지원하는 요청을 우선 연결한다. 민감파일 직접 조회처럼 주입 파라미터가 없는 요청은 기존 `verify_incident`에 무리하게 넣지 않고 별도 조회 계획 지원 여부를 확인한다.

본문·필수 헤더·인증 정보가 없는 요청은 자동 생성하지 않는다. 접근제어 검증은 소유자/비소유자 세션과 대상 객체 등 추가 입력이 필요하다. 현재 시점의 재현은 과거 사건의 성공 여부를 그대로 입증하지 않으며 보고서에 두 시점을 분리한다.

관측 SIEM 이벤트는 도구가 전송한 트래픽으로 기록하지 않는다. 별도 이벤트 저장소에서 실제 검증 run/incident/asset에 연결한다. 실제 실행 이력에 source를 확장할 경우 [agent_history.py](../backend/routers/agent_history.py), 저장 허용 목록, [global_lookup.js](../frontend/static/js/global_lookup.js)의 표시를 함께 정리한다.

## 10. 데이터·실행·운영 경계

- **분석 위치:** 현행 브라우저 파일 파싱과 달리 제안은 EventProbe 서버로 로그를 전송한다. 사설망으로 접속해도 서버 전송이며, 사용자 PC 내부 처리라고 표시하면 안 된다. 허가된 배포 서버에서 분석하고 전송 보호를 구성한다.
- **저장:** 기본은 세션 분석, 저장은 명시적 선택. 원문/정규화 결과에 접근 권한·보존 기한·삭제 정책을 적용한다. 재시작 시 임시 분석 데이터 정리도 설계한다. asset hash가 있어도 host/path 필드까지 익명화되는 것은 아니다.
- **공유 사용:** 배치·이벤트·원문·계획·결과마다 소유자 권한 검사. 공용 토큰만 사용하는 배포에서는 개인별 격리를 보장하지 못하므로 다중 사용자 저장 기능 전 식별 체계를 정해야 한다.
- **외부 전송:** 원문 로그·URL·헤더·PCAP을 외부 AI/위협조회에 보내지 않는다. MVP는 AI 호출 없이 동작한다. 추후 요약을 추가해도 허용된 비식별 집계만 사용하고 기존 egress 가드를 검증한다.
- **입력 처리:** 로그는 신뢰할 수 없는 문자열이다. HTML은 텍스트로 표시하고 제어문자·길이·중첩·정규식 실행 비용·파일 크기를 제한한다. CSV 내보내기는 수식 실행을 방지한다. 분석용 제한과 원문 보관을 구분해 증거를 조용히 변조하지 않는다.
- **실행 범위:** 사용자가 확정한 서비스만 검증한다. 입력 URL, 리다이렉트, DNS 변경으로 범위가 넓어지지 않도록 실행 시 검사한다. 메타데이터/관리 주소 등은 기존 정책과 승인 범위를 적용한다.
- **예산:** 동시성·호스트별 속도·전체 요청 수·시간 상한·중지 버튼을 계획에 포함한다. 재시도/리다이렉트/기준 요청도 총 요청 예산에 계산한다. 인증값은 로그에서 자동 재사용하지 않는다.
- **OOB:** 필요 유형은 별도 선택. 내부 대상은 승인된 자가호스팅 수집기를 사용한다.
- **자동화:** 정기 실행 주기·대상·총 예산·알림 채널은 아직 미정이다. 구현 제안의 기본값은 수동 분석/수동 실행이며, 미정 값으로 정기 스캔이나 외부 알림을 시작하지 않는다.

## 11. 순차 구현 계획과 완료 기준

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1. 입력 기반 | 익명화 샘플 fixture, 3종 파서, 공통 스키마, 오류/충돌 처리 | 세 샘플의 act/disposition/status/count를 정확히 보존; 실패 행 누락 0 |
| 2. 읽기 전용 MVP | 이벤트 분석 탭, 규칙, 그룹, 요약, 상세, 필터/내보내기 | 분석 중 대상/외부 AI 요청 0; 전체 수량 대사 가능; 저우선 복원 가능 |
| 3. 자산·저장 | 관측 자산 연결, 운영 인벤토리, 보존/권한, 감사 기록 | 미등록/오래된 정보로 자동 제외하지 않음; 타 사용자 원문 접근 차단 |
| 4. 선별 검증 | 계획 생성, 지원 유형 검사, 승인/예산, 기존 실행 연결 | 미확정 대상 실행 불가; 요청 상한/중지 검증; event→run→결과 추적 |
| 5. 운영 조정 | 실제 판정 표본으로 규칙/대표선정 조정, 성능 측정 | 누락과 절감 효과를 함께 보고; 정책 변경 전후 비교 가능 |

각 단계는 이전 완료 기준을 충족한 뒤 진행한다. 일정은 로그량·입력 포맷·권한 체계 확인 후 산정한다. 정기 실행과 외부 알림은 조건이 정해진 뒤 별도 범위로 착수한다.

### 필수 검수 시나리오

1. IPS `Permit`을 차단으로 표시하지 않고, status 없음은 null로 유지한다.
2. WAF `action=N/A`가 `disposition=Block`을 덮어쓰지 않는다. 1레코드/13회가 구분된다.
3. IDS `Inconclusive`가 HTTP 코드나 도구 검증 결과로 변환되지 않는다.
4. Host 불일치·치환 IP·프로토콜 미확정 상태에서 실행 계획을 활성화하지 않는다.
5. 404 단순 스캔은 조건부 저우선이지만 403/429/5xx는 같은 규칙으로 제외하지 않는다.
6. 차단 이벤트와 허용 이벤트가 섞인 그룹에서 허용 이벤트가 숨겨지지 않는다.
7. 같은 endpoint의 서로 다른 공격 값은 보존하고, 동일 파일 재가져오기는 중복 집계하지 않는다.
8. 인용부호·쉼표·이스케이프·`==`·중복 헤더·다국어·깨진 행을 처리하고 실패 위치를 표시한다.
9. 스크립트 형태의 탐지명과 CSV 수식 문자열이 실행되지 않는다.
10. 요청 예산 초과·취소·계획 변경·범위 밖 리다이렉트·타 사용자 접근이 차단된다.
11. 재현되지 않은 결과를 ‘안전’ 또는 ‘해결 완료’로 바꾸지 않는다.

### 효과 측정

- 분모를 입력 레코드/장비 발생 횟수/독립 그룹으로 구분한다.
- 담당자 검토 시간, 그룹당 검증 요청 수, 파싱 실패율, 정보 보완 비율을 측정한다.
- 검토 대상 절감률과 함께 **저우선 목록 표본 재검토에서 발견된 중요 이벤트 비율**을 보고한다.
- 성능은 고정 장비에서 1천/1만/10만 레코드의 시간·메모리·취소 응답을 기록한 뒤 지원 상한을 정한다.
- 최초 적용은 기존 판단과 비교하는 관찰 모드로 진행한다. 규칙 변경 이력과 되돌릴 정책 버전을 보관한다.

## 12. 착수 시 기본 결정

확정 제안은 **별도 이벤트 분석 탭, 읽기 전용 분석부터 구현, 조건부 저우선 처리, 미등록 자산 자동 제외 금지, 기존 검증 엔진의 선택적 재사용**이다.

운영 담당자·자산 데이터 소유자·보존 기간·허용 대상/요청 예산은 운영 적용 전에 정한다. 이 값이 없어도 1~2단계의 샘플 기반 파서와 화면 개발은 진행할 수 있다. 원문 저장·다중 사용자 운영·실제 대상 검증은 해당 설정과 접근 체계가 갖춰진 범위에서 제공한다.
