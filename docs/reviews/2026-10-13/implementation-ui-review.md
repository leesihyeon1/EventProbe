# EventProbe 구현 및 UI 평가

검토일: 2026-10-13. 기준 커밋: `e92c6b6`.

## 판정

**사내 실사용은 보류해야 한다.** Python 기반을 유지하면서 공통 반출 검사, 제한된 계획 DSL, 로컬 실행기를 추가한 방향은 타당하다. 다만 응답·도메인 비반출이라는 핵심 요구를 아직 충족하지 못하고, 계획 모드의 일부 동작은 스키마에만 존재한다. UI는 독립된 업무 화면으로 재설계하기보다 기존 화면에 패널을 추가한 상태다.

이 문서는 평가 결과다. 제품 코드, `.env`, 실제 실행 기록은 수정하지 않았다. 실제 정보 유출 사고가 발생했다는 뜻이 아니라, 합성 데이터가 외부 전송용 입력에 남고 검사도 통과하는 경로를 확인했다는 뜻이다.

## 발견 사항

### F1. [P1] strict 반복 모드에서 응답 원문 일부가 다시 AI 입력으로 들어감

- 위치: `backend/core/agent.py:205`, `:569`, `:701`; `backend/core/confirm.py:356`.
- `_strict_context()`는 관측의 `untrusted_response_excerpt`를 제거하지만 `verified_results`를 그대로 보존한다.
- 확증 엔진은 명령 출력의 계정명, 파일 내용 일부, 응답 Location 등의 실제 값을 `rounds[].techniques[].evidence`에 포함한다. 이 결과가 다음 planner 호출에 다시 포함된다. 객체 접근 판정의 정책 설명도 동일 경로로 남는다.
- 재현: 합성 응답 `uid=1001(review_private_account)`로 실제 `confirm.decide()` 결과를 만들었다. strict 변환과 외부 목적지 guard를 모두 통과한 입력에 해당 문자열이 남았다. 응답 공유 체크박스의 켜짐 여부와 별개다.
- 수정 방향: 외부 입력을 허용 필드만 포함하는 별도 스키마로 새로 구성한다. 원문 증거와 자유 형식 설명은 로컬 저장소에만 남긴다. 응답에서 파생된 라벨도 외부로 보내지 않는 요구라면 반복 모드를 외부 제공자에서 차단해야 한다.

### F2. [P1] 비식별 요청의 attack_tokens에 실제 값과 도메인이 포함됨

- 위치: `backend/core/public_shape.py:164`, `:187`; `backend/core/agent.py:260`.
- 공격 신호의 일부분을 추출하는 것이 아니라, 따옴표 등 신호가 하나라도 있으면 값 전체의 앞 200자를 복사한다.
- 중첩 JSON 객체는 `str(dict)`, 배열은 `json.dumps(list)`에 따옴표가 생기므로 정상 업무 데이터도 공격 토큰으로 분류된다.
- 재현: 중첩 객체와 배열에 넣은 합성 비밀값 및 `payroll.corp.test`가 계획 생성 입력의 `attack_tokens`에 남았다. strict guard도 차단하지 않았다.
- `register_canary()`의 제품 코드 호출부도 없어, 실행 대상 호스트가 자동 등록된다는 주석상의 방어는 연결되지 않았다. 패턴 검사만으로 비반출을 보장할 수 없다.
- 수정 방향: 검증된 공격 신호를 열거 코드로 바꾸고 실제 값을 통째로 복사하지 않는다. 중첩 데이터, 경로 세그먼트, 필드명에도 식별 정보가 들어갈 수 있다는 전제로 허용 규칙과 거부 처리를 정의한다.

### F3. [P1] 현재 반출 기본값과 실행 화면이 요구사항에 맞지 않음

- 위치: `backend/core/ai_egress.py:34`; `backend/core/agent_models.py:58`; `frontend/templates/index.html:398`.
- 설정 누락이나 오타가 있으면 `permissive`로 작동한다. 검토한 로컬 실행 화면도 실제 `PERMISSIVE`로 표시됐다.
- 응답 비반출 계획 모드는 기본 선택이 아니고, 응답 발췌 전송 옵션도 존재한다. 사내 전용 배포의 필수 정책이 사용자 선택 사항으로 취급된다.
- 수정 방향: 사내 배포는 strict 또는 외부 호출 금지를 기본값으로 삼고 잘못된 설정은 시작 시 거부한다. 응답 공유는 서버에서 금지한다. F1/F2 때문에 strict 설정 변경만으로 해결됐다고 판단하면 안 된다.

### F4. [P1] 계획 모드가 confirm/access를 정상 동작처럼 받아들이지만 실행하지 않음

- 위치: `backend/core/agent.py:236`, `:405`.
- 계획 생성 프롬프트는 `confirm`과 `access`를 허용한다. 그러나 `_exec_plan_step()`에는 observe/probe/finish 처리만 있다.
- payload가 없는 confirm은 기본 조회 한 번 후 `observed`로 끝난다. payload가 있더라도 일반 probe 경로를 타며, 기존 반복 모드의 차등 확증 두 회차를 수행하지 않는다.
- access는 설정한 객체 URL 및 소유자/비인가 계정 비교를 수행하지 않고 seed를 한 번 조회한다.
- 재현: confirm은 seed 조회 1회, access도 비인가 계정의 seed 조회 1회만 발생했다. 실제 대상 요청은 사용하지 않았다.
- 수정 방향: 검증된 공통 action 실행기를 두 모드가 공유하게 하거나, 미지원 동작을 계획 검증에서 명시적으로 거부한다. 실행되지 않은 검사에 완료 상태를 부여하지 않는다.

### F5. [P2] 계획 생성이 AI 호출 예산과 집계에서 빠짐

- 위치: `backend/core/agent.py:430`.
- `generate_plan()`을 예산 검사 전에 실행하고 `ai_calls`도 증가시키지 않는다.
- 재현: `max_ai_calls=0`인데 계획 생성 함수가 호출됐고 기록은 0회였다.
- 반복 모드에 있는 실행 deadline 기반 `fail_after`도 계획 생성 경로에는 없다. 이 시간 제한 문제는 코드 검토 결과이며 별도 지연 재현은 하지 않았다.
- 수정 방향: 호출 전 예산 예약 및 저장, 남은 실행 시간으로 timeout 제한, 실패·재시도도 포함한 실제 호출 집계를 적용한다.

### F6. [P2] 계획 단계와 HTTP 증거의 step_id 연결이 끊김

- 위치: `backend/core/agent.py:445`, `:468`, `:490`, `:530`.
- `_plan_loop()`의 지역 `step_id`와 `fetch()`가 참조하는 `_run()`의 `step_id`가 다르다.
- 재현: action에는 단계 ID가 있지만 observation에는 빈 ID가 저장된다. request ID와 evidence ID는 남으므로 증거 자체가 사라지는 것은 아니지만 단계별 감사 추적은 깨진다.
- 수정 방향: 실행 컨텍스트 또는 fetch 인자로 단계 ID를 명시적으로 전달한다.

### F7. [P2] 이전 agent.css가 신규 스타일을 실제로 덮어씀

- 위치: `frontend/templates/index.html:872`; `frontend/static/css/agent.css:5`; `frontend/static/css/style.css:1850`.
- 새 스타일을 작성한 뒤 이전 모달용 CSS를 페이지 끝에서 다시 로드한다. 동일한 `.agent-config`, label, status, event 클래스가 충돌한다.
- 브라우저 계산값 확인: config padding은 신규 `0 10px 10px` 대신 `16px`, label은 flex 대신 block, 상태 텍스트는 본문색 대신 파란색으로 적용됐다.
- 수정 방향: 기존 모달 CSS를 정리하거나 별도 범위로 제한하고 agent 스타일의 소유 파일을 하나로 통합한다.

### F8. [P2] 자율 검증이 기존 요청 화면의 레이아웃에 종속됨

- 위치: `frontend/templates/index.html:34`, `:377`; `frontend/static/css/style.css:106`, `:1834`, `:1896`.
- 자율 검증에서도 260px 페이로드 사이드바와 전송 툴바가 유지되고, 그 안에 340px 작업 패널이 추가된다.
- 1440x900에서 새 작업 설정은 작은 패널 안에 세로로 길게 배치되고, 우측 작업 공간은 활용되지 않는다. 작업 미선택 시 빈 공간 자체는 정상이나, 작업 생성 폼까지 같은 좁은 패널에 넣은 선택은 개선이 필요하다.
- 836px 폭에서는 세 열이 압축되고 전송 툴바가 잘린다. 390x844에서는 전역 사이드바가 그대로 남아 메뉴 글자가 세로로 꺾이고 주요 입력·명령이 화면 밖으로 나간다. agent 내부만 바꾸는 미디어 쿼리로 해결되지 않는다.
- 모바일 사용이 범위 밖이어도 노트북 분할 화면에 대한 대응은 필요하다. 기존 레이아웃에서 물려받은 문제도 포함한 평가다.
- 수정 방향: 자율 검증을 독립 작업 화면으로 만들고 수동 요청 편집기의 사이드바/전송바는 해당 화면에서만 표시한다.

## UI 평가

현재 화면이 거칠게 느껴지는 근거는 다음과 같다. 색상 취향만의 문제가 아니다.

- 정보 위계가 약하다. 목표, 실행 상태, 판정, 증거가 비슷한 크기·강조로 표현되고 일부 라벨은 10~12px로 작다.
- 텍스트 버튼, 이모지 아이콘, 파란 강조색, 녹색 실행 버튼의 사용 규칙이 통일되지 않았다. 제품 표기도 화면은 SecAPITester, 저장소는 EventProbe다.
- 작업 목록은 잘린 목표와 상태만 보여 준다. 같은 목표의 실행을 시간, 요청 요약, 모드로 구별하기 어렵다.
- 이벤트 뷰는 종류별 요약 뒤에 `JSON.stringify()`한 내용을 보여 주는 방식이다(`frontend/static/js/agent.js:254`). 기본 화면의 Diff 기능은 있지만 자율 검증 증거에 연결된 전용 비교 화면은 아니다. 이 부분은 실제 저장 증거를 열지 않고 렌더링 코드를 확인했다.
- 기존 수동 요청 폼을 참조해서 새 작업을 시작하는데, 자율 검증 화면에서는 body/params 등 전체 실행 입력을 검토하기 어렵다.
- 계정·객체 정책, 반출 모드, 계획 모드 설명까지 긴 좁은 설정 영역에 모여 있다. 보안 도구의 복잡성을 UI가 충분히 정리하지 못했다.

권장 화면 구조:

1. 전역 탐색은 수동 분석 / 자율 검증 / 실행 기록 / 설정으로 구분한다.
2. 자율 검증 목록에는 실행 이름, 로컬 요청 요약, 시작 시간, 상태, 확증/의심/미확정 수를 표로 제공한다.
3. 새 작업은 본문에서 대상 요청, 허용 범위, 계정/객체 정책, 요청 한도를 검토하고 시작하게 한다. 고급 항목만 접는다.
4. 실행 상세는 상단 상태·한도·중단, 중앙 단계 타임라인, 선택 단계의 요청/응답/차이/판정 근거로 구성한다. 원문은 로컬에서만 표시한다.
5. 반출 정책은 간결한 고정 상태 표시로 제공하고, 실제 전송 예정 구조를 로컬 미리보기로 확인할 수 있게 한다.
6. 한 종류의 아이콘, 13~14px 본문, 일관된 간격·컨트롤 높이를 사용한다. 결과의 의미가 색상만으로 구별되지 않게 한다.

Python 또는 vanilla JS 자체가 UI 문제의 원인은 아니다. 이번 수정만을 위해 Go 전환이나 전면 프레임워크 교체가 필요하지는 않다. backend는 유지하고 화면 책임과 CSS 경계를 먼저 정리하는 편이 범위가 명확하다.

## 검증 결과 및 한계

- 기존 신규 기능 관련 테스트: **72 passed**, 3 warnings. 전체 backend suite 실행 결과는 아니다.
- 추가 요구 계약 검사: **8 failed**. 기본 반출 모드 1개, 중첩 JSON/배열 2개, 응답 근거 반출 1개, confirm/access 각 1개, 예산 1개, 증거 연결 1개다. 기능 미충족을 확인하는 의도적인 실패 검사이며 서로 독립적인 결함 8개라는 뜻은 아니다.
- 초기 재현 도구가 Windows asyncio의 loopback socketpair까지 막는 문제가 있어 이를 보정한 뒤 재실행했다. 위 결과는 보정 후 실제 assertion 실패 결과다.
- 재현 파일: `review_contract_checks.py`. 일반 `test_*.py` 수집에 섞이지 않도록 이름을 분리했으며 아래 명령으로 명시 실행한다.
- UI: 실행 중인 로컬 서버에서 요청/분석, 자율 검증, 새 작업 폼을 확인했다. 1440x900, 기본 약 836px 폭, 390x844에서 점검했고 임시 viewport는 복원했다. 관찰한 흐름의 브라우저 오류 로그는 없었다.
- 실제 NVIDIA API 호출, 실제 공격 요청, 저장된 요청·응답 증거 열람은 하지 않았다. API 모델의 계획 생성 품질, 실제 인증 환경, 중단/재개 전체 흐름, 모든 RAG 경로의 비반출 보장은 이번 검사로 증명되지 않았다.
- 특히 재개 시 계획 재생성과 실행 위치 복구는 추가 검토가 필요하다. 현재 `_plan_loop()`는 진입할 때마다 계획을 생성하고 entry부터 시작한다.

```powershell
.\.venv\Scripts\python.exe -m pytest docs/reviews/2026-10-13/review_contract_checks.py -q --tb=short
```

기존 테스트가 통과하는 이유 중 하나는 plan 실행 테스트가 판정 함수를 mock해서 분기만 확인한다는 점이다. `backend/tests/test_plan_run.py:36`의 테스트는 실제 confirm/access 실행 의미나 원문 비반출 계약까지 보증하지 않는다. 따라서 통과 수만으로 구현 완료를 판정하면 안 된다.

## 유지할 부분과 수정 순서

유지할 부분: 중앙 AI 호출 검사 지점, Pydantic 계획 검증, 임의 코드 실행 없는 조건 분기, 동일 출처 제한, HTTP 요청 한도, 로컬 증거 저장/삭제, 기존 확증 엔진. 전체를 버릴 필요는 없다.

1. F1~F3를 고쳐 반출 계약을 먼저 닫는다. 모드별·채널별 실제 outbound payload 캡처 회귀 검사를 추가한다.
2. F4~F6를 고쳐 action 실행 의미, 예산, 증거 연결을 일치시킨다. 계획 재개/중단과 실제 판정기를 결합한 오프라인 통합 검사도 추가한다.
3. F7을 정리하고 F8의 화면 구조를 재설계한다. 운영 화면에 필요한 목록·상세·오류·빈 상태를 함께 만든다.
4. 합성 HTTP 서버와 가짜 AI 응답으로 종단간 검사한 뒤, 승인된 시험 환경에서만 실제 제공자와 대상 검증을 수행한다.

UI 참고 기준: [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md). 본 문서의 결함 판정은 해당 지침에 대한 인상 평가가 아니라 로컬 소스, 실행 화면, 재현 검사에 근거한다.
