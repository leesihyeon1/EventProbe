# ARTEX 실화면·소스 비교: 탭 및 자율검증 구현 검토

검토일: 2026-10-18. 대상은 현재 EventProbe 작업 트리와 `D:/ARTEX-main/ARTEX-main` 로컬 소스다. 기존 미커밋 변경을 기준으로 읽었으며 이 검토에서 제품 코드는 변경하지 않았다.

## 1. 검토 범위와 결론

- 로그인된 `http://localhost:8787`의 대시보드, 작업 목록, 작업 상세 개요·테스트 자산, 전역 트래픽, 전역 발견 화면을 직접 확인했다.
- EventProbe `http://127.0.0.1:8010`의 Asset과 최신 작업 상세를 확인하고, 로컬 실행 DB의 해당 작업 메타데이터를 읽었다. 내부 응답·인증값을 문서에 복사하지 않았다.
- ARTEX 화면은 LLM 미설정/모델 사용 불가, 트래픽 수집 꺼짐, 발견 0건이었다. 이 환경에서 ARTEX가 로그인 SQL 취약점을 실제로 찾았다는 비교 실험은 하지 않았다. 화면 구조와 소스 기능을 참고한 검토다.
- ARTEX의 탐색 그래프는 작업의 의도·근거 관계이고 자산 커버리지 그래프는 자산 관계다. URL 사이트맵과 같은 그래프로 합치지 않는다.
- EventProbe에는 작업 관리, 작업별 발견·사이트맵·커버리지, 증거 내보내기, 재검증 시작, 보관, 템플릿, 사내 이벤트, 감사 기능이 이미 있다. 필요한 것은 기존 기능의 연결과 누락된 전역 조회·검증 실행 능력이다.

**최우선은 발견한 로그인 폼을 실제 검사와 증거 판정까지 연결하는 것이다. 탭 추가만으로 현재 탐지 실패가 해결되지는 않는다.**

## 2. 확인한 결함

### P1. 최신 실패는 요청 범위 설정만으로 설명되지 않는다

작업 `e4ddf50e18c946c4bbba562650e038d6`의 저장 기록:

| --- | --- |
| 범위 / 쓰기 | `same_origin` / 허용 |
| 목표 | 일반 취약 신호 확인 및 후속 검사 |
| 실행 | 6단계, 대상 요청 6회, 검AI 호출 8회 |

따라서 이 작업은 폼을 발견했지만 SQL 검사를 한 번도 실행하지 못했다. 앞선 `request_only` 작업에 대한 설명을 이 실행에도 적용하면 안 된다. 증거 ID가 틀린 이유가 모델 오기인지 계약 문제인지는 현재 저장된 거절 코드만으로 확정할 수 없다.

현재 로컬 SQL 절차는 명시적인 SQL/인증 목표이며 AI가 꺼졌거나 호출 예산이 0일 때만 기본 계획기를 대신한다. 일반 목표 또는 AI 활성 상태에서는 발견한 폼에 대한 최소 검사 진행이 보장되지 않는다. 근거: [agent.py:1323](C:/Users/lsh/Downloads/dev/EventProbe/backend/core/agent.py:1323), [agent.py:1456](C:/Users/lsh/Downloads/dev/EventProbe/backend/core/agent.py:1456).

필요한 개선:

1. 폼의 입력 유형·제출 방법·필수값·발견 출처를 저장하고, 로그인 폼을 별도 검사 후보로 등록한다. `tfUName` 같은 필드명을 문자열 추정에만 맡기지 않는다.
2. 후보마다 계획/실행/관측/판정/보류 사유를 저장한다. 일반 목표에서도 허용된 기본 검사가 계속 누락되는지 추적한다.
3. AI에는 호출별 `obs_1` 같은 짧은 참조를 제공하고 로컬에서 실제 증거 ID에 정확히 매핑한다. 존재하지 않는 참조를 가까운 값으로 보정하거나 임의 근거를 붙이지 않는다.
4. 같은 계획 오류가 반복되면 범위·목표·예산 안의 등록된 검사 절차로 진행할 수 있는지 판단한다. 진행 불가 시 어떤 입력을 왜 검사하지 못했는지 결론에 남긴다.
5. 로그인 성공 쿠키·리다이렉트는 의심 신호로 보고, 실패 대조군과 세션을 분리한 보호 자원 확인으로 확정 근거를 수집한다. `RetURL` 자체나 200/302만 성공 증거로 쓰지 않는다.

### P1. 브라우저 기능이 존재해도 실제 사용할 수 있는지 알기 어렵다

이번 작업은 브라우저 실패가 `Error`로만 남았다. 현재 구현은 초기 페이지와 최대 두 GET 경로를 열어 같은 출처의 GET/HEAD document/script/XHR/fetch를 제한 수집한다. 폼 조작, DOM 생성 입력 추출, 계정 세션 연계는 없다. 근거: [agent_browser_recon.py:17](C:/Users/lsh/Downloads/dev/EventProbe/backend/core/agent_browser_recon.py:17).

추가로 브라우저 요청은 수집 완료 후 작업 카운터에 반영되고, `asyncio.to_thread`를 사용한다. 일반 HTTP 경로의 전송 전 예약·중단 처리와 동등한 내구성을 가정할 수 없다. 실제 브라우저 종료·취소·시간 한도·실행 중 예약 기록을 통합하는 작업이 필요하다.

시작 전 Chromium 실행 가능 여부, 버전, 수집 가능 항목을 표시하고 실패를 브라우저 미설치/실행 실패/탐색 시간 초과/정책 차단 등으로 구분한다. 원본 오류 문자열은 외부 모델에 전달하지 않는다. 탐색 UI에는 HTTP 관측과 브라우저 관측의 성공·누락을 각각 표시한다.

대시보드의 실행 중/검토 필요/미검사/브라우저 실패/최근 발견 요약은 우선 자율 검증 개요에 넣는다. 전체 통합 데이터가 생긴 뒤 운영 대시보드를 추가할 수 있으며 기본 접속 화면을 바꾸지 않는다.

## 6. 구현 순서와 완료 조건

### A. 탐색에서 검증으로 이어지는 실행 흐름

- 현재의 발견 엔드포인트에 폼/입력 스키마와 검사 후보 상태를 연결한다. 범위 밖 폼은 발견 정보로 보존하되 실행 불가 이유를 표시한다.
- 모델 참조 ID 계약, 동일 오류 반복 대응, 로그인 폼 우선순위, 목표별 최소 검사와 완료 조건을 정의한다. AI가 선택할 수 있는 프로필과 실제 실행기의 비용 계산을 일치시킨다.
- 브라우저 준비 상태, 로컬 세션 연계, 요청 예약, 중단·종료, 명확한 실패 코드를 구현한다.
- 로그인 검사는 실패 대조군/격리 세션/두 회차 확인을 유지하고, 필요 시 허용된 동일 출처 보호 자원으로 성공 여부를 확인한다.
- 완료 조건: 로컬 취약 로그인과 수정된 로그인 두 서버를 실제 HTTP 및 Chromium으로 검사한다. HTML 폼, JS 폼/API, 회전 토큰, 302, 실패 문구 반사, 잘못된 AI 참조, 모델 사용 불가, 한도·중단을 포함한다. 취약 판정뿐 아니라 수정된 서버의 오탐 방지를 검증한다.
- 제공된 공개 실습 URL은 필요 시 별도의 제한된 실환경 확인 대상으로 사용한다. 현재 검토에서는 새로운 로그인 시도나 SQL 요청을 보내지 않았다.

### B. 공통 자산·트래픽·발견 조회

- 기존 저장 이벤트를 원본으로 유지하며 자산/엔드포인트/폼/트래픽/발견의 조회용 색인을 추가한다. 원본 run·event·actor·policy 버전과 연결한다.
- 도메인·메서드·실제 경로·입력 구조를 구별하고, URL 값이나 응답 내용을 무작정 그래프 노드 이름으로 확장하지 않는다. 경로 템플릿은 그룹화 정보이며 원본 식별을 대신하지 않는다.
- 작업공간별 접근 범위를 지키는 전역 API, 서버 검색·페이지 조회, 오래된 실행의 재색인, 보관·복원·삭제 시 관계 보존을 구현한다.
- 완료 조건: 서로 다른 두 작업이 같은 자산을 공유하며 각각의 출처와 판정을 보존한다. 새로고침/서버 재시작 후에도 검색·필터·이력이 유지되고, 다른 작업공간 데이터가 섞이지 않는다.

### C. 메뉴 및 작업 상세 재구성

- B의 전역 API가 준비된 항목부터 독립 메뉴를 추가한다. 빈 메뉴만 먼저 늘리지 않는다.
- 기존 보고서·재검증·템플릿·이벤트·보관 기능의 진입점을 유지하고 새 화면과 연결한다.
- 실행 기록의 중복 탭을 묶고 폼/계획/미실행 사유를 화면에 노출한다. 기술 코드에는 사용자용 오류명과 가능한 복구 동작을 연결한다.
- 완료 조건: 요청 → 자율 작업 → 폼/계획 → 트래픽/증거 → 발견 → 재검증 → 보고서를 뒤로가기와 직접 링크로 이동할 수 있다. 긴 URL과 모바일에서도 조작 가능해야 한다.

### D. 운영 기능 보강

- 작업별 모델 지연·토큰·실패·재계획과 브라우저/검증 도구 상태를 영속 기록한다. 현재 메모리 집계와 작업별 시도 기록을 구분한다.
- 준비 상태를 확인할 수 있는 설정·감사 화면을 만들고, 이후 필요에 따라 승인된 정기/사내 이벤트 검증과 알림을 연결한다.
- 완료 조건: 서버 재시작 후에도 어떤 작업이 어떤 모델/절차/정책으로 멈췄는지 확인된다. 토큰 미제공은 0이 아니라 미제공으로 표시한다.

## 7. 데이터 비반출 조건

응답 본문, DOM, 스크린샷, 도메인/IP, 쿠키·인증값, 서버 헤더 원문, 테스트에서 나온 내부 데이터는 로컬에 보존한다. 외부 NVIDIA에는 승인된 경로 구조·필드 스키마·정적 기술 이름·판정 상태·짧은 참조·남은 예산만 전달한다. 외부 모델용 필드와 로컬 UI용 필드는 별도 스키마로 관리하며 URI/필드명 자체의 민감 정보 처리 규칙도 유지한다.

로그인 여부와 취약성 확정은 로컬 판정기가 결정하고, 원문 반사·본문 길이·HTTP 성공 코드만으로 확정하지 않는다. 화면 조회와 내보내기는 추가 대상 통신이나 AI 호출을 유발하지 않아야 한다.

## 8. 검토의 한계와 재현 자료

이번 산출물은 구현 검토서다. 제품 코드 수정, 실제 대상에 대한 새 검사, ARTEX 모델 설정 변경, 전체 회귀 테스트는 수행하지 않았다. 기존 문서의 테스트 개수를 이번 검토의 성공 근거로 사용하지 않는다.

최신 EventProbe 실패는 저장된 기록과 UI를 교차 확인했다. ARTEX는 실제 화면 구조와 로컬 소스를 대조했으며, 실행 성능을 입증하지 않았다. 실행 중인 ARTEX UI와 소스의 일부 번역이 다르므로 동일 빌드라고 단정하지 않는다.

## 9. 구현 진행 기록 (2026-10-18)

이 절은 위 검토 당시의 관찰과 구분되는 작업 기록이다. **A-D 전체 완료를 의미하지 않는다.**

### 이번 반영

- A: 기본 AI 계획기에 관측 근거 단축 ID와 정확한 역매핑을 적용했다. 존재하지 않는 ID를 임의 근거로 대체하지 않는다. 발견된 `POST` 로그인 폼의 계정 필드를 일반 목표에서도 우선 검사 후보로 올리고, 같은 검사를 반복하지 않게 했다. 다른 실행의 증거 ID를 내면 실행하지 않고 재계획하며, 반복 오류는 부분 결론과 함께 일시정지한다.
- A: 로컬 테스트에서 `tfUName`/`tfUPass` ASP 폼의 취약·비취약 대조군을 확인했다. 브라우저 번들이 없는 이 PC에서 설치된 Edge로 탐색할 수 있게 했으며, 실제 Edge 실행과 로컬 페이지 GET 수집을 확인했다. 준비 상태 API와 UI, 브라우저 오류명을 추가했다. 렌더링 후 DOM의 POST 폼은 제출하지 않고 동일 출처 검사 후보로 등록한다. 브라우저 GET은 전송 전에 로컬 이벤트/요청 예산에 예약하고 중단 시 추가 라우트를 거절한다. 작업별 폼 후보에 대기·검사 중·판정·중단·예산 부족 상태를 저장 이벤트에서 계산해 표시한다.
- B: 기존 작업 엔드포인트를 값 없는 전역 Asset 색인으로 재색인하고, 생성·갱신·보관·삭제·아카이브 가져오기와 연동했다. 작업공간 필터, 서버 검색·페이지 조회, 작업별 출처를 제공한다. Asset 화면 기본값은 `전체 작업`이고, 작업 선택 시 기존 작업별 사이트맵이 유지된다. POST 본문은 필드명만 작업별 사이트맵과 전역 자산 상세에 노출한다.
- 검증: Asset의 값 비노출·소유권·두 작업 통합·재시작·보관·삭제·과거 작업 재색인 테스트, 브라우저 대체 실행·전송 전 예약·폼 상태 테스트, 프런트엔드 회귀를 추가/실행했다. 전체 백엔드 1,136개 통과 후 폼 상태 테스트를 추가해 관련 테스트를 다시 통과했고, 프런트엔드 140개가 통과했다. 로컬 UI는 `http://127.0.0.1:8012`에서 확인했다.

### 남은 완료 조건

1. A: 폼의 입력 유형 영속화, JS 제출/API 통신의 안전한 연결, 브라우저 요청의 중단 중 진행 상태와 시간 한도에 대한 종단 검증, 회전 토큰 및 보호 자원 확인. 폼 검사 상태는 이벤트에서 파생되며 별도 원본 기록은 없다. DOM 폼 등록은 수동 탐색이며 JS 핸들러의 실제 제출 URL을 증명하지 않는다. 실HTTP/Chromium 취약·수정 서버 종단 테스트가 필요하다. 공개 실습 사이트에 대한 취약점 시도는 이번 반영에서 수행하지 않았다.
2. B: 공통 트래픽·발견 색인과 전역 조회, 자산-요청-판정 관계 및 재검증 비교 이력. 현재 전역 Asset은 경로 구조와 작업 출처를 보여주지만 전체 판정 상태를 합산하지 않는다.
3. C: 권장 왼쪽 메뉴와 작업 상세 6개 탭의 재구성, 직접 링크/뒤로가기/모바일 검증. 현재는 Asset 기본 조회만 전역으로 바뀌었다.
4. D: 작업별 모델·브라우저·검증 절차 영속 진단을 통합한 설정·감사 화면. 브라우저 준비 상태만 추가됐으며 전체 운영 화면은 미완료다.

이후 작업은 A의 실제 요청 예약과 폼 검사 상태를 먼저 닫고, B의 공통 조회 API를 안정화한 다음 C의 탭을 연결하는 순서가 적절하다. 미완료 조건을 충족하기 전에는 `전체 계획 완료` 또는 실 대상의 취약점 검증 성공으로 표시하지 않는다.

## 10. 추가 구현 진행 (2026-10-19)

**전체 계획은 여전히 미완료다.** 다음 항목을 기존 이벤트 원본과 작업공간 접근 범위를 유지하면서 추가했다.

- A: HTML 및 렌더링된 DOM의 POST 폼에 대해 필드 이름·유형·필수 여부·발견 출처를 로컬 작업 기록에 저장한다. 필드 값은 폼 스키마에 넣지 않는다. 작업 상세 `탐색 · 입력`에서 검사 상태와 함께 표시한다. 브라우저 응답 콜백과 페이지 탐색의 시간 초과를 명시적인 실패 코드로 남기도록 고쳤다.
- B: 기존 이벤트에서 값 없는 트래픽·발견 조회 색인을 생성하고 오래된 작업을 시작 시 재색인한다. 작업별 출처, 자산 ID, 작업공간, 보관 상태, 서버 검색·페이지 조회를 적용했다. 새 관측·판정·처리 상태 변경·아카이브 가져오기·삭제·보존 정리와 색인을 연동했다. 트래픽 원문은 항목을 열 때만 기존 작업별 이벤트 API에서 조회한다.
- C: 왼쪽 메뉴에 전역 `발견`, `트래픽`을 연결했다. 작업 상세에는 `탐색 · 입력`, 작업별 `트래픽`을 추가했다. 선택한 상세 탭을 URL 조각에 담고 뒤로가기로 복원한다. 기존 탭과 명령은 유지했다.
- D: `설정 · 감사` 화면에서 브라우저·AI·반출 정책 준비 상태와 작업별 정책 버전, 모델, 호출·거절 횟수, 모델 대기 시간, 브라우저 상태, 중단 사유를 조회한다. 제공되지 않은 토큰 수는 `미제공`으로 둔다.
- 검증: 전체 백엔드 1,139개 통과 후 추가한 두 테스트와 작은 변경을 관련 테스트에서 다시 확인했다. 전체 프런트엔드 143개가 통과했다. `git diff --check`도 통과했다.

남은 완료 조건은 JS 이벤트로 제출되는 폼/API의 실제 목적지 검증, 회전 토큰·보호 자원 확인을 포함한 취약·수정 서버의 실 HTTP/Chromium 종단 실험, 수동·일괄 요청까지 통합하는 트래픽 저장, 발견 재검증의 조건 비교와 중복 묶기, 권장 6개 탭으로의 최종 재구성, 모바일 시각 검증이다. Playwright CLI는 이 환경에서 패키지 레지스트리 접근 거부로 실행되지 않아 브라우저 시각 검증을 수행하지 못했다.
