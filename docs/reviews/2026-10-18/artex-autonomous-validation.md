# ARTEX 비교 및 자율검증 개선

## 검토 범위

- EventProbe의 로컬 최근 실행 기록과 `backend/core/agent.py`, `confirm.py`, `agent_outcome.py`.
- `D:/ARTEX-main/ARTEX-main/agent/planner.go`, `worker.go`, `finding_workflow.go`, `wrapup.go`, `skills/api-recon/SKILL.md`.
- 제공된 Theori ARTEX 백서의 물리 페이지 5(구조), 28(외부 모델 반출 위험), 33(운영 통제).
- 외부 대상 스캔이나 NVIDIA 호출 없이 합성 HTTP 응답 및 실제 SQLite 쿼리로 검증했다. 실제 사용자의 취약 사이트에서 성공했다고 주장하지 않는다.

## 확인한 문제

1. SQL 목표에서도 모델의 반복 행동 선택으로 호출 예산을 소모했다. 기존 일부 실행은 SQL 대신 XSS를 실행했다. 기존 목표 유형 제한과 반복 복구 수정은 유지했다.
2. POST 로그인 폼은 발견하더라도 실제 제출 요청으로 연결하지 못하고 중단했다. 단순 페이지 쿼리를 검사하는 것은 로그인 제출 검사를 대신하지 못한다.
3. 기존 SQL 확증은 MySQL 시간/에러 검사까지 묶어 19개 요청을 사용한다. 기본 예산 24개에서는 선행 탐색과 반복 probe 이후 확증이 불가능해지기 쉽다.
4. 동일 세션에서 로그인 성공 쿠키가 다음 대조 요청에 남으면 참/거짓 비교가 오염될 수 있다.

## ARTEX에서 적용한 원칙

| ARTEX 구조 | EventProbe 적용 |
| --- | --- |
| planner.go: 발견 변화에 따라 다음 intent 생성 | 명시적인 SQL 단일 목표에 로컬 입력별 대조 검사 목록 적용 |
| worker.go: 한 intent에 집중하고 실제 관측을 즉시 기록 | SQL 외 유형으로 전환하지 않으며 요청·관측·검증 이벤트 연결 유지 |
| finding_workflow.go: 실제 트래픽 ID와 발견 사항 연결 | 대조군과 두 회차 결과의 evidence_ids를 결론에 연결 |
| wrapup.go: 예산 종료 시 결과 보존과 마무리 | 기존 로컬 최종 결론 유지, 시작 전 전체 검사 비용 확인, 예산 부족은 부분 완료 |
| api-recon: 관측한 입력을 다음 실행으로 연결 | 같은 출처 HTML GET/POST 폼의 입력·선택값·본문 발견 |

ARTEX의 외부 모델에 원문을 제공하는 방식이나 셸 기반 자유 실행은 도입하지 않았다. Python을 Go로 재작성할 필요도 없다.

## 구현 범위

- 기본 planner의 **반복 모드 + 명시적 SQL 단일 목표 + 구조화된 별도 goals 없음**에서 외부 모델 없이 검사한다. 승인된 계획과 주입된 사용자 정의 planner는 자동 대체하지 않는다.
- 문자열/숫자/주석 컨텍스트를 별도 프로필로 분리했다. 각 프로필은 원본·참·거짓 대조를 두 번 수행하며 두 번째는 상수와 순서를 바꾼다. 최초 기준 요청 포함 7회다.
- 관측한 POST 폼을 우선한다. 새 필드를 임의로 만들지 않고 CSRF 필드는 공격 입력에서 제외한다.
- POST 폼은 같은 출처 탐색과 쓰기 허용이 모두 필요하다. 기존 경로·메서드 정책도 적용한다. 원본 요청 한정 모드에서는 다른 폼으로 이동하지 않는다.
- 각 확증 요청 전 클라이언트 쿠키를 보존하고 요청 후 복원한다. GET에서 발견한 POST 폼은 제출마다 원본 페이지를 읽어 알려진 CSRF 필드를 갱신한다. 이 경우 프로필당 14회로 예산을 예약한다.
- 회전하는 CSRF 값만 다른 POST 폼을 새 엔드포인트로 중복 등록하지 않는다.
- 단순 입력 반사를 제거한 본문을 비교한다. 로컬 SQL 프로필은 두 회차 모두 의심 신호가 있어야 suspicious로 기록한다.
- 길이/상태 차이를 인증 우회 확정으로 승격하지 않는다. 실제 보호 자원 조회 등 독립적인 성공 조건은 별도 검증이 필요하다.
- POST 처리 여부가 불명확한 오류에서 자동 재시도하지 않는다. 기존 재개 시 모호한 쓰기 보호도 유지한다.

## 검증

- 전체 백엔드: 1,121 passed (기존 deprecation 경고 3개).
- 프런트엔드: 136 passed.
- `git diff --check`: 통과.

`backend/tests/test_agent_local_sql.py`는 실제 SQLite의 문자열/숫자 취약 쿼리와 매개변수 바인딩 대조군, 로그인 폼, 일회용 CSRF, 로그인 쿠키 오염, 원본 요청 범위, 쓰기/경로/메서드 제한, 외부 출처, 반사 오탐, 요청 예산, 불명확한 POST를 검사한다. HTTP 계층은 MockTransport를 사용하며 외부 모델 호출은 테스트 실패로 처리한다.

로그인 fixture에서는 사용자 필드의 대조 검사가 초기 GET 포함 15회 안에 끝난다. 나머지 필드와 프로필이 예산을 넘으면 부분 결론으로 종료한다. 이것은 전체 사이트 검사 완료가 아니다.

## 남은 제약과 다음 검증

- JavaScript 생성 폼, SPA, 브라우저 기반 인증은 아직 이 로컬 경로에서 수집하지 않는다.
- 알려진 이름의 CSRF 토큰 갱신과 쿠키 복원은 서버 측 세션 상태를 롤백하지 않는다. 일회용 세션, CAPTCHA, 계정 잠금, MFA는 별도 승인된 fixture와 처리 필요.
- SQL 시간/에러/DB별 문법 전체를 새 로컬 절차가 포괄하지 않는다. 기존 full 확증 프로필은 남아 있다.
- 복합 목표·구조화된 goals·승인 계획은 기존 흐름을 유지하므로 이번 개선을 전체 자율검증 엔진의 완성으로 해석하면 안 된다.
- 실제 배포 중인 서버에는 코드 재시작/재배포가 필요하다. 기존 저장 실행 결과는 소급 변경하지 않는다.
- 후속 우선순위: 독립적 로그인 성공 oracle, 로컬 브라우저 요청 수집, 입력별 미검사 사유/필요 예산 표시, 여러 계정의 세션 초기화 계약.

## 로그인 폼 검증 추가

- 첫 페이지에서 관측한 같은 출처 링크를 따라 로그인 HTML을 읽고, 비밀번호 필드가 있는 POST 폼을 인증 검사 대상으로 고른다.
- 계정 식별 필드에는 실패 대조군과 `admin'-- `, OR 조건 입력을 두 회차로 전송한다. 각 제출은 관측한 폼의 다른 값과 CSRF를 유지한다.
- `로그인 인증 우회`처럼 SQL 단어가 없는 목표도 로컬 인증 절차에 연결한다. SQL 목표인 경우는 기존 SQL 카테고리로 판정한다.
- 선택적으로 지정한 `protected_marker`가 실패 대조군과 요청에 없고 공격 응답에만 있을 때, 로그인 성공 신호와 함께 확정한다. 표식 없이 쿠키, 상태, 이동, 실패 문구가 바뀐 경우는 의심으로 남긴다.
- HTML GET 링크와 POST 폼, 실제 SQLite 취약/매개변수 바인딩 로그인, 모델 호출 0회를 회귀 테스트로 확인한다. 브라우저 JavaScript 생성 폼은 여전히 대상이 아니다.
